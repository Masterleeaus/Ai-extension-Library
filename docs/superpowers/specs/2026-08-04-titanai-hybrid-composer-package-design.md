# TitanAI Hybrid Composer Package Design

## Goal

Convert the shared TitanAI Hybrid host overlay into a nested private Laravel Composer package while preserving the separate marketplace identities and responsibilities of AIAgent, AIChatPro, and Chatbot.

## Authoritative layout

```text
Ai-extensions/
├── extensions/
│   ├── AIAgent/
│   ├── AIChatPro/
│   └── Chatbot/
└── packages/
    └── titanai-hybrid-core/
        ├── composer.json
        ├── src/
        ├── config/
        ├── database/migrations/
        ├── tests/
        ├── bin/
        └── docs/
```

`packages/titanai-hybrid-core` becomes the only authoritative copy of the shared foundation. `foundation/TitanAI-Hybrid` is removed after deterministic conversion and must not be regenerated by repository materialisation.

## Namespace and compatibility

The package uses the independent namespace `TitanAI\Hybrid\`. The three extensions are updated to import the package namespace. A Composer autoload compatibility file aliases the shared legacy `App\Domains\TitanAI\...` symbols to their new package classes so host code can migrate incrementally. Chatbot-owned classes that already use other `App\Domains\TitanAI` subnamespaces remain inside Chatbot and are not moved.

## Package responsibilities

The package owns only shared infrastructure:

- registry contracts and `UnifiedRegistry`;
- event contracts and failure-isolated event bus;
- unified memory repository and memory scopes;
- diagnostics;
- cross-extension orchestration;
- scheduled expired-memory cleanup;
- package configuration and migration.

AIChatPro retains connector implementations and interactive workspace behavior. Chatbot retains customer conversations, channels, PWA, skills, and immediate interaction. AIAgent retains durable workflows, actions, and native memory. WorkCore remains authoritative for operational business records.

## Laravel integration

`TitanAI\Hybrid\TitanAIServiceProvider` is registered through Laravel package discovery and may also be registered explicitly by extension providers so deployments that disable discovery remain supported. The provider merges package configuration, loads package migrations, registers aliases and singletons, exposes publish tags, registers the purge command, and schedules cleanup.

The package supports Laravel 10 through 13. Laravel 13 requires PHP 8.3; the package itself retains a PHP 8.1 floor so existing Laravel 10–12 hosts remain viable.

## Extension dependency contract

Each core extension receives `titanai-package.json` containing:

```json
{
  "package": "titanai/hybrid-core",
  "constraint": "^1.0",
  "provider": "TitanAI\\Hybrid\\TitanAIServiceProvider"
}
```

The extension service providers reference the package namespace. The dependency metadata is separate from `extension.json` to avoid relying on undocumented marketplace manifest keys.

## Materialisation

The existing verified MiniUp Pass 3 overlay remains the recovery source. After the overlay is restored, `scripts/package_titanai_hybrid.py` deterministically:

1. validates the legacy foundation and three extension folders;
2. creates the Composer package;
3. rewrites only shared foundation namespace references;
4. writes Composer and extension dependency metadata;
5. removes the legacy foundation directory;
6. supports a `--check` mode that validates the committed state without rewriting it.

The GitHub Actions materialisation workflow runs this conversion every time, validates `composer.json`, lints package and extension PHP, runs the package verification suite, then runs existing extension and ecommerce checks.

## Testing and rollback

Tests cover package metadata, namespace migration, provider paths, compatibility aliases, extension imports, dependency metadata, deterministic materialisation, and absence of a duplicate foundation tree. The previous Pass 3 archive and MiniUp overlay remain unchanged as rollback evidence. A rollback may restore the previous repository commit; no production host should remove the old overlay until the complete WorkCore Composer integration passes.

## Branch and merge policy

Implementation occurs on short-lived branches with small focused commits. After verification and review, pull requests are merged into `main`. Future package work should follow the same short-branch, frequent-merge pattern rather than accumulating long-lived branches.
